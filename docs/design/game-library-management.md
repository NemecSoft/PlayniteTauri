# 游戏库管理（Game Library Management）

日期：2026-08-13
状态：设计定稿（权威文档）

> 本文档是"以游戏库管理为基础"这一**根本业务原则**的权威描述。
> 游戏库的概念不只是一个可选项，而是整个游戏系统的**地基**——所有游戏都必须
> 归属某个游戏库，所有启动路径都必须以游戏库为根。这样游戏库在任意磁盘/目录
> 之间迁移时，**不需要改动任何游戏数据**，只需改游戏库的 `path`。

## 一、核心业务原则（必须严格遵守）

### 原则 1：任何游戏必须在某个游戏库里
- 游戏库（`GameLibrary`）= 一个游戏存放的**根目录**（如 `D:\Games1`、`D:\Games2`、
  `E:\Games`，任意盘符 / 任意路径都行）。
- **每个游戏都必须属于某一个游戏库**（`Game.gameLibrary` 存游戏库**名称**，必填）。
- 一个游戏只属于一个游戏库。

### 原则 2：游戏路径必须以游戏库为根
- 游戏的启动项路径 / 工作目录一律用 **`{游戏库名}\子目录\exe`** 形式的**占位符**，
  **不允许**用脱离游戏库的绝对路径（如直接写 `D:\Somewhere\Game.exe`）。
- 这样游戏库换盘 / 换目录时，只需改游戏库的 `path`，游戏数据无需改动。

### 原则 3：路径解析始终基于游戏库
- 客户端 / 校验 / 脚本工作目录在解析路径时，**先按游戏库名匹配 `{名称}` 占位符**
  得到游戏库根目录，再拼接剩余子路径。
- 绝对路径只在"用户主动浏览文件系统、且该路径恰好落在游戏库内"时才被转成相对路径
  存回；落在游戏库外则不允许作为游戏路径。

## 二、数据模型

### GameLibrary
```rust
pub struct GameLibrary {
    pub id: String,   // 唯一 id（lib-<uuid>）
    pub name: String, // 用户可编辑名称，作为 {name} 占位符 token
    pub path: String, // 游戏根目录（绝对路径），如 D:\Games
}
```
- 存储于 `config.json` 的 `AppSettings::game_libraries: Vec<GameLibrary>`。

### Game 与游戏库的关系
- `Game.gameLibrary: Option<String>` 存游戏库**名称**，每个游戏绑定一个库。
- `Game.actions[*].path` 用 `{库名}\相对子路径` 表达，`workingDir` 同理。

### 典型路径
```
{库1}\Grain Rot\Helden.exe          // 启动项 exe
{库1}\Grain Rot                     // 工作目录（自动从 path 派生）
{库2}\SomeGame\Game.exe
```
- 占位符 `{名称}` 不区分大小写，后端 `process::resolve_path` 按名称匹配游戏库根，
  再归一化剩余相对路径为绝对路径（如 `D:\Games1\Grain Rot\Helden.exe`）。

## 三、为什么这样设计（迁移友好）

| 场景 | 绝对路径 | 游戏库占位符 |
| --- | --- | --- |
| 游戏库从 `D:\Games` 迁到 `E:\Games` | 每个游戏路径都要改 | **只改游戏库的 `path` 一处** |
| 增加第二块盘放更多游戏 | 各自硬编码 | 新增一个游戏库即可 |
| 客户端/管理端跨机器 | 路径失效 | 只要配置游戏库 path 一致即可 |

**这是本项目"绿色存储 + 可移植"理念在游戏库维度的体现**：游戏数据（`library/library.db`）
与游戏库根目录解耦，迁移时数据不动，只动游戏库配置。

## 四、管理端约束（UI 落地）

- **"通用"页**：`所属游戏库` 为**必填**单选下拉。
- **"指令"页**：
  - `{游戏库名}\` 前缀**只读显示**（取自"通用"页所选游戏库），用户**不能**在此修改游戏库。
  - 用户只需填写游戏库下的**相对路径**（子目录 + exe），如 `Grain Rot\Helden.exe`；
    前端自动拼上 `{游戏库名}\` 前缀存库。
  - **"浏览…"** 从游戏库根目录开始选文件；选中后自动转成"库名 + 相对路径"存回。
  - **"校验"** 基于游戏库根 + 相对路径，在真实文件系统上检查 exe 是否存在。
  - **工作目录**由 `path` 自动派生为 `{游戏库名}\子目录`（占位符形式），不填绝对路径。
- **脚本页**：脚本工作目录联动游戏库（优先用 is_play_action 路径解析出的工作目录，
  其次游戏库根），脚本里的相对路径（如 `./tool.exe`）在游戏实际目录下解析。

## 五、游戏库管理（CRUD）

- 游戏库的增删改在**顶层"游戏库管理"标签页**进行（独立于游戏编辑器）。
- 表格列：ID / 名称（`{名称}` 占位符）/ 路径 / 操作（编辑 / 删除）。
- 路径可用 Tauri 文件选择对话框选择。
- 删除游戏库前二次确认；若删除后相关游戏失去库，需要提示（当前实现：游戏仍保留，
  但 `gameLibrary` 引用失效，客户端解析该游戏路径会失败——迁移友好场景下应提前
  调整游戏库归属，删除前二次确认）。

## 六、后端命令

- `admin_get_game_libraries`：返回全部游戏库。
- `admin_save_game_library`：新增（id 空）或更新（按 id）。
- `admin_delete_game_library`：按 id 删除。
- `admin_validate_action`：校验启动项路径（基于游戏库根 + 相对路径）。
- `save_game`：保存含多条 `actions` 的游戏（`Game` 整体 JSON 持久化）。
