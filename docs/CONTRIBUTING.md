# 文档同步约定

> **原则**：**每次代码修改 / 新增功能 / 变更设计，都必须同步更新设计文档。**
> 设计文档与代码同等重要，是项目的"活"规范，不允许出现代码与文档脱节。

## 何时必须更新文档

以下任一情况发生，**必须**同步更新对应文档：

1. **新增功能** → 新建功能设计文档，或在 `docs/design/` 对应文档补充该功能的
   目标、实现方案、关键代码位置。
2. **修改数据模型**（`Game` / `GameName` / `GameAction` / `AppSettings` 等字段增删改）
   → 更新 `docs/design/data-models.md`。
3. **修改搜索逻辑** → 更新 `docs/design/search.md`。
4. **修改主题 / 多语言 / 视图 / 存储 / 构建** → 更新对应 `docs/design/*.md`。
5. **任何可观察的行为变更** → 在 `docs/CHANGELOG.md` 追加一条变更记录
   （日期 + 变更内容 + 相关文档链接）。
6. **目录结构变化**（新增/删除/移动文件）→ 更新 `docs/design/directory-structure.md`。

## 更新流程（每次修改的标准动作）

```
1. 编码修改
2. 更新相关设计文档（design/*.md）
3. 在 CHANGELOG.md 追加变更记录
4. 提交（git commit message 中引用对应文档，如 "feat: 多名称; docs: 更新 data-models"）
```

## 文档结构规范

- 每个文档以 `# 标题` 开头，随后 `## 目标`、`## 实现方案`、`## 关键点` 等小节。
- 代码片段使用围栏代码块并标注语言（rust / ts / powershell / bash）。
- 引用相关文档用相对链接（如 `[搜索系统](./search.md)`）。
- 涉及"为什么这样做"（决策依据）的内容应写入，便于后人理解。

## 检查

每次修改后，可在 PR / 提交前自查：
- [ ] 本次改动是否影响数据模型？→ 已更新 `data-models.md`
- [ ] 是否新增/变更功能？→ 已在对应文档体现
- [ ] 是否在 `CHANGELOG.md` 追加了记录？
- [ ] 目录是否有增减？→ 已更新 `directory-structure.md`
